1. 什么是 ANR

ANR（Application Not Responding，应用无响应）是系统对“应用在规定时间内没有完成某项关键任务”的判定。注意几个关键点：

  • 裁判是系统，不是应用：ANR 由 system_server 进程里的 AMS（ActivityManagerService）、ActiveServices、BroadcastQueue 以及 native 层的 InputDispatcher 判定。
  • 只有“系统派发给应用的任务”才会触发：输入事件、广播、Service 生命周期等。你自己在主线程 Thread.sleep(10000)，如果期间没有任何系统任务派发过来，不会产生 ANR，只是卡。
  • 主线程不一定是罪魁祸首：主线程可能在等锁、等 Binder、等 IO，或者整机 CPU / 内存压力大导致进程根本没被调度到。
💡 一句话理解 系统给应用派活时先“埋一颗定时炸弹”（发一条延迟消息），应用按时干完就“拆弹”（移除消息），超时没拆，炸弹“引爆”——进入 appNotResponding 流程：抓 trace、写日志、弹窗或静默杀进程。

2. 核心机制：埋炸弹 / 拆炸弹 / 引爆

除 Input 外，四类组件的 ANR 都遵循同一个模型：

以 startService 为例：AMS 在通知 App 执行 onCreate/onStartCommand 前调用 bumpServiceExecutingLocked() → scheduleServiceTimeoutLocked() 埋雷；App 主线程执行完生命周期后通过 serviceDoneExecuting() 回调 AMS 拆雷。

// ActiveServices.java（简化，Android 14 之前的经典写法）
void scheduleServiceTimeoutLocked(ProcessRecord proc) {
    if (proc.mServices.numberOfExecutingServices() == 0 || proc.getThread() == null) {
        return;
    }
    Message msg = mAm.mHandler.obtainMessage(ActivityManagerService.SERVICE_TIMEOUT_MSG);
    msg.obj = proc;
    // 💣 埋雷：前台 20s，后台 200s
    mAm.mHandler.sendMessageDelayed(msg, proc.mServices.shouldExecServicesFg()
            ? mAm.mConstants.SERVICE_TIMEOUT
            : mAm.mConstants.SERVICE_BACKGROUND_TIMEOUT);
}

private void serviceDoneExecutingLocked(ServiceRecord r, boolean inDestroying, ...) {
    ...
    if (r.app.mServices.numberOfExecutingServices() == 0) {
        // ✂️ 拆雷
        mAm.mHandler.removeMessages(ActivityManagerService.SERVICE_TIMEOUT_MSG, r.app);
    }
}
Android 15+：AnrTimer新版本中这些 sendMessageDelayed/removeMessages 被统一封装进 com.android.server.utils.AnrTimer（mActiveServiceAnrTimer.start()/cancel()），并可选地由 native 定时服务实现，还能在超时时对进程做“冻结 + 先抓 trace”。但“埋 / 拆 / 爆”的模型完全不变。

2.3 Broadcast 超时（BroadcastQueue）

经典实现（Android 13 及以前 BroadcastQueue.java）只对有序广播和静态注册接收者（它们本质上是串行派发的）计时：派发给某个接收者前 setBroadcastTimeoutLocked()，接收者 onReceive 返回后（或 goAsync() 的 PendingResult.finish()）调用 AMS.finishReceiver() 拆雷。

Android 14 引入 BroadcastQueueModernImpl（按进程分队列），目前 main 分支已删除旧的 BroadcastQueueImpl。现代队列有两个值得注意的细节（已对照源码核实）：

// BroadcastRecord.java —— 哪些投递“视为已送达”，根本不计 ANR 时
boolean isAssumedDelivered(int index) {
    return (receivers.get(index) instanceof BroadcastFilter) // 动态注册的接收者
            && !ordered                                       // 非有序广播
            && (resultTo == null);                            // 不需要回传结果
}

// BroadcastQueueModernImpl.java —— “软超时”：先按 CPU 排队时间延长一次再引爆
private void deliveryTimeoutSoftLocked(BroadcastProcessQueue queue, int softTimeoutMillis) {
    if (queue.app != null) {
        // 进程处于 runnable 但没拿到 CPU 的时间不算 App 的错，最多延长一次
        final long cpuDelayTime = queue.app.getCpuDelayTime() - queue.lastCpuDelayTime;
        final long hardTimeoutMillis = MathUtils.constrain(cpuDelayTime, 0, softTimeoutMillis);
        mAnrTimer.start(queue, hardTimeoutMillis);
    } else {
        deliveryTimeoutLocked(queue);
    }
}
✅ 实践启示普通的 context.registerReceiver() + sendBroadcast() 在 Android 14+ 上不会因为 onReceive 慢而触发广播 ANR（但阻塞主线程依然可能导致 Input ANR）。静态接收者、有序广播依旧受 10s / 60s 约束。

2.4 ContentProvider 超时

进程启动时 attachApplicationLocked() 中若该进程有待发布的 Provider，AMS 会发送 CONTENT_PROVIDER_PUBLISH_TIMEOUT_MSG（10s）；App 在 handleBindApplication → installContentProviders → publishContentProviders 后由 AMS 移除该消息。超时则杀进程。这也是为什么在 ContentProvider.onCreate() 里做重活（很多 SDK 借 Provider 自动初始化）会拖慢冷启动甚至导致进程被杀。

2.5 Input 超时（InputDispatcher）

Input ANR 不走 AMS Handler，而是在 native 层 InputDispatcher 里判定。Android 11 重构后（AnrTracker）逻辑为：事件发送到窗口的 InputChannel 后进入该连接的 waitQueue，并记录超时时间点；App 处理完通过 finishInputEvent 回传 finished 信号后从 waitQueue 移除。

⚠️ 两个常见误解 1）不是“主线程卡 5 秒就 ANR”：必须有输入事件在等待。用户不碰屏幕，卡 10s 也不会产生 Input ANR。
2）没有焦点窗口也会 ANR：按键事件需要焦点窗口，如果 App 有焦点应用但迟迟没有焦点窗口（例如 Activity 启动太慢），5s 后报 Application does not have a focused window。

4.1 SIGQUIT 与 Signal Catcher

ART 虚拟机启动时会在每个进程中创建一个名为 Signal Catcher 的线程，并把 SIGQUIT (3) 在其他线程中屏蔽。收到 SIGQUIT 后，它会挂起所有线程（SuspendAll）、遍历线程打印 Java + native 栈，再通过 tombstoned 管道写入 /data/anr。你也可以手动触发：

# 让某进程打印线程栈（需 debuggable 或 root）
adb shell kill -3 <pid>
# 或使用 debuggerd 获取 Java 栈
adb shell debuggerd -j <pid>

# 查看 ANR 文件（普通设备无权限直接读，推荐 bugreport）
adb shell ls -l /data/anr/
adb bugreport ./bugreport.zip      # 解压后在 FS/data/anr/ 下

# logcat 中定位
adb logcat -b events | grep am_anr
adb logcat -s ActivityManager | grep -A 20 "ANR in"
小知识源码 ProcessErrorStateRecord 中有一个兜底：若 trace 文件生成失败（tracesFile == null），会直接 Process.sendSignal(pid, Process.SIGNAL_QUIT)，让栈至少打印到 logcat。

5. 常见原因

🧵 主线程耗时操作

磁盘 IO（SharedPreferences commit、数据库）、网络、大 JSON 解析、Bitmap 解码、复杂布局 inflate。

🔒 锁竞争 / 死锁

主线程 synchronized 等待被子线程长期持有的锁；两把锁交叉持有导致死锁。

📞 同步 Binder 调用

主线程调用 getContentResolver().query()、PackageManager、AccountManager 等，对端（含 system_server）忙或卡住。

📦 SharedPreferences apply

apply() 的写盘任务会在 Activity.onStop/Service 生命周期中被 QueuedWork.waitToFinish() 同步等待。

📣 Receiver / Service 里做重活

onReceive、onCreate、onStartCommand 都运行在主线程。

🐢 系统资源紧张

整机 CPU 满载、内存不足导致频繁 GC / kswapd、IO wait 高（iowait），主线程虽然“没做什么”但抢不到 CPU。

📨 消息队列堆积

主线程 Handler 被大量消息淹没，单个消息不慢但累计很慢，或一个超长消息排在 Input 前面。

🧩 第三方 SDK 初始化

在 Application.onCreate / ContentProvider.onCreate 中同步初始化。

6.3 线程状态速查

状态含义排查方向
Runnable正在执行或等 CPU看栈顶是否耗时计算；结合 schedstat 第二项（等待调度时间）判断是否抢不到 CPU
Blocked等待 synchronized 监视器锁找 held by thread N，追踪持锁线程
Waiting / TimedWaitingObject.wait() / LockSupport.park() / sleepJ.U.C 锁、CountDownLatch、Future.get()
Native执行 native 代码看 native 栈：binder_ioctl（Binder 同步调用）、epoll_wait（空闲）、read/fsync（IO）
Suspended被 GC / 调试器挂起看 GC 日志、内存压力
⚠️ 注意“栈漂移”trace 是在超时之后才抓的，抓到的主线程栈可能是“压死骆驼的最后一根稻草”，甚至是 nativePollOnce（主线程已空闲）。这时需要结合超时前一段时间的消息调度历史来判断，这也是 Matrix、Raster 等方案记录“消息历史”的原因。

7.2 编码原则

  • IO / 网络 / 数据库一律放到协程 Dispatchers.IO 或线程池；主线程只做 UI。
  • BroadcastReceiver 中耗时工作使用 goAsync() + 后台线程（仍受超时约束），或交给 WorkManager。
  • startForegroundService() 后尽快在 onStartCommand 中调用 startForeground()。
  • SharedPreferences 迁移到 DataStore / MMKV，避免 QueuedWork 阻塞。
  • 主线程避免 synchronized 与后台线程共享粗粒度锁，避免主线程同步 Binder。
  • SDK 初始化懒加载 / 使用 App Startup 并异步化。
class SyncReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        val pending = goAsync()                       // 延长生命周期，但仍受 10s/60s 约束
        CoroutineScope(Dispatchers.IO).launch {
            try {
                Repository.sync(intent)               // 耗时操作放到 IO 线程
            } finally {
                pending.finish()                      // ✂️ 一定要 finish，否则必 ANR
            }
        }
    }
}

8.1 方案对比

方案原理优点缺点
Looper Printer 监控（BlockCanary 思路）Looper.setMessageLogging()，在 >>>>> Dispatching / <<<<< Finished 间计时简单，能抓“卡顿”只是卡顿≠ANR；字符串拼接有开销；抓栈时机滞后
Watchdog 线程（ANR-WatchDog）子线程定期向主线程 post 任务，超时未执行即判卡零侵入误报/漏报多，与系统判定不一致
SIGQUIT 信号监听（Matrix / xCrash）系统判 ANR 时会向进程发 SIGQUIT，App 自己也捕获它与系统判定时机一致，可拿到完整 trace需 native hook；需二次确认是否真的是本进程 ANR
ApplicationExitInfo（Android 11+）下次启动读取 REASON_ANR 及 trace官方 API、准确非实时，拿不到 ANR 前的上下文
Google Play Console / Firebase系统上报无需接入只覆盖 Play 渠道，信息有限

8.2 Looper 监控示例

object LooperMonitor {
    private const val THRESHOLD_MS = 300L
    private var startTime = 0L

    fun install() {
        Looper.getMainLooper().setMessageLogging { msg ->
            if (msg.startsWith(">>>>>")) {
                startTime = SystemClock.uptimeMillis()
                StackSampler.start()                       // 后台线程周期采样主线程栈
            } else if (msg.startsWith("<<<<<")) {
                val cost = SystemClock.uptimeMillis() - startTime
                StackSampler.stop()
                if (cost > THRESHOLD_MS) {
                    Reporter.reportJank(cost, msg, StackSampler.dump())
                }
            }
        }
    }
}
// Android 10+ 也可通过反射/系统 API Looper.setObserver（@hide）获得更低开销的回调。

8.3 SIGQUIT 检测原理（Matrix / xCrash）

sequenceDiagram
    autonumber
    participant SS as system_server (AMS)
    participant DBG as debuggerd / tombstoned
    participant K as Kernel
    participant SH as App 自装的 SIGQUIT handler
    participant SC as ART Signal Catcher
    SS->>DBG: dumpStackTraces(pid)
    DBG->>K: 向 App 进程发送 SIGQUIT
    Note over SH: App 提前 pthread_sigmask 解除 SIGQUIT 屏蔽
并 sigaction 注册 handler
    K->>SH: 回调 handler（先于 Signal Catcher）
    SH->>SH: 记录 ANR 疑似事件 + 主线程栈 / 消息历史
    SH->>SH: 二次确认：轮询 ActivityManager.getProcessesInErrorState()
或检查主线程 Message 的 when 是否严重滞后
    SH->>SC: syscall(tgkill, pid, signalCatcherTid, SIGQUIT)
把信号转发回 Signal Catcher
    SC->>DBG: 正常输出 traces，系统流程不受影响

// 简化示意（参考 Matrix SignalAnrTracer / xCrash xc_trace）
static struct sigaction sOldHandler;

static void anrSignalHandler(int sig, siginfo_t *info, void *uc) {
    // 1. 判断是否来自其他进程（system_server/debuggerd），排除自己 kill -3
    if (info->si_pid != getpid()) {
        onAnrDumpTriggered();          // 通知 Java 层：抓栈、二次确认、上报
    }
    // 2. 转发给 Signal Catcher，保证系统 trace 正常生成
    syscall(SYS_tgkill, getpid(), findSignalCatcherTid(), SIGQUIT);
}

void installAnrMonitor() {
    sigset_t set;
    sigemptyset(&set);
    sigaddset(&set, SIGQUIT);
    pthread_sigmask(SIG_UNBLOCK, &set, nullptr);   // ART 默认屏蔽了 SIGQUIT

    struct sigaction sa{};
    sa.sa_sigaction = anrSignalHandler;
    sa.sa_flags = SA_SIGINFO | SA_ONSTACK | SA_RESTART;
    sigaction(SIGQUIT, &sa, &sOldHandler);
}
❗ 为什么需要“二次确认”收到 SIGQUIT 不等于本进程 ANR：其他进程 ANR 时，系统也会 dump 相关进程（firstPids/lastPids）；手动 kill -3 也会触发。Matrix 的做法是检查 ActivityManager.getProcessesInErrorState() 中是否有本进程的 NOT_RESPONDING 记录，并结合主线程消息队列头部消息是否已严重超时。

8.4 Android 11+ 官方兜底：ApplicationExitInfo

fun reportLastAnr(context: Context) {
    if (Build.VERSION.SDK_INT < Build.VERSION_CODES.R) return
    val am = context.getSystemService(ActivityManager::class.java)
    am.getHistoricalProcessExitReasons(context.packageName, 0, 5)
        .filter { it.reason == ApplicationExitInfo.REASON_ANR }
        .forEach { info ->
            val trace = info.traceInputStream?.bufferedReader()?.use { it.readText() }
            Reporter.reportAnr(
                timestamp = info.timestamp,
                description = info.description,   // 例如 "Input dispatching timed out ..."
                trace = trace
            )
        }
}

9. 总结 & Checklist

🧠 原理

系统派活 → 埋雷 → App 完成回调拆雷 → 超时引爆 → appNotResponding。Input 由 native InputDispatcher 判定，其余由 AMS 侧判定。

⏱️ 阈值

Input 5s · 前台广播 10s · 后台广播 60s · 前台 Service 20s · 后台 Service 200s · Provider 发布 10s（杀进程）。

🔍 分析

Reason → Load/CPU/iowait → main 线程状态 → 锁/Binder/IO → 警惕栈漂移。

🛡️ 治理

StrictMode 开发期拦截；线上 SIGQUIT 实时监控 + ApplicationExitInfo 兜底 + 消息历史还原现场。
