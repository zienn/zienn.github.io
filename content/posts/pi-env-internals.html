1. 它解决什么问题：整体架构

pi 的 Durable 运行时通过 ExecutionEnv 接口操作文件和执行命令（packages/durable/src/env/index.ts：interface ExecutionEnv extends FileSystem, Shell {}，包含 readTextFile、openBinaryReader、writeFile、listDir、exec、cleanup 等方法），默认实现是本地的 NodeExecutionEnv。pi-env 让 Agent 留在本地，而把“手和脚”放到另一台机器上：

  • 本地：RemoteExecutionEnv（TS）实现同一个 ExecutionEnv 接口，通过 Connection 收发帧。
  • 远端：Rust 守护进程 pi-env serve --token <hex>，经 ssh 启动，用 stdin/stdout 通信。
  • README 的承诺：结果与“在远端机器上跑 NodeExecutionEnv”一致，只有错误消息文本可能不同。支持 Linux、macOS、Android（Termux）、Windows 的 x86-64 与 arm64，各平台守护进程预编译在 bin/ 中随包发布。

分工原则写在 docs/semantics.md：客户端负责路径解析、abort 检查点、错误映射（toFileError）、readFile 的尺寸与解码、writeFile 按 512 KiB 分块、行读取器、超时与结果优先级；守护进程负责系统调用、进程、溢出文件（spill）、行扫描、从 NodeFileWatcher 移植的监视器，以及用 encoding_rs 解码输出。换言之：能在本地算的语义都留在 TS，必须贴近文件的才放 Rust。

2. 线协议：同步行 + 二进制帧

2.1 先同步：PI-ENV <token>

ssh 登录后 shell 的 rc 文件可能往 stdout 打印横幅、motd 之类的“噪声”。所以守护进程第一件事是输出一行 PI-ENV <token>\n，客户端丢弃这行之前的一切（docs/protocol.md）。token 由客户端每次启动随机生成（randomBytes(16) 的 hex），因此噪声里不可能恰好出现它；connection.ts 在找同步标记时若噪声超过 1 MiB 就放弃。

2.2 帧格式

字节偏移字段类型说明
0lengthu32 BE后续字节数（type 起算），范围 9..=16 MiB
4typeu81 request · 2 result · 3 error · 4 event · 5 cancel · 6 ping
5idu32 BE请求 id，用于多路复用
9jsonLengthu32 BEJSON 段长度，0 表示 {}
13jsonUTF-8操作参数 / 结果元数据
13+jsonLengthpayloadbytes其余字节：文件内容、命令输出等

所有整数大端，单帧最大 16 MiB。类型：1 request、2 result、3 error、4 event、5 cancel（可带 {mode:"kill"}）、6 ping。JSON 放元数据，payload 放文件内容/命令输出等二进制，避免了 base64 膨胀。守护进程的解析非常保守：

2.3 多路复用与取消

每个请求带一个 id，result/error/event 用同一 id 回传，于是一条管道上可以并发几十个请求，流式输出就是同 id 的一串 event 帧。协议文档强调了一个容易出错的竞态：每个请求在开始执行前就先登记，因此紧跟其后的 cancel 不会丢（test/remote.test.ts 里有 “aborts commands cancelled right after they are sent”）。

2.4 输出调度：控制队列 vs 批量队列

daemon/src/output.rs 只有一个 stdout 写线程，但有两个队列。控制帧（小结果、错误、ping）优先；负载超过 64 KiB 的回复和 exec 结果排在输出后面（保证“结果晚于它的输出”）。未开窗口的命令输出在未发送数据超过 4 MiB 时阻塞生产者：

// daemon/src/output.rs
pub fn wait_for_room(&self, stop: &AtomicBool) {
    let mut queues = self.queues.lock().unwrap();
    while queues.bulk_bytes > BULK_LIMIT && !queues.closed && !stop.load(Ordering::SeqCst) {
        queues = self
            .drained
            .wait_timeout(queues, Duration::from_millis(100))
            .unwrap()
            .0;
    }
}

这就是背压：慢网络下 yes 这种命令不会把守护进程内存撑爆，而 ping 依旧能及时发出，不会被误判为失联。

2.5 调度与存活

线程模型

文件操作在 16 个 worker 线程上；exec、pty、watch 各自独占线程（16 MiB 栈）。ptyWrite/ptyResize/ptyForeground 由读帧线程按到达顺序直接应答，键盘输入不会乱序。

有序分块写

run_in_order 让同一句柄的 writeChunk 串行执行；某块失败后句柄被“毒化”，后续块一律 EBADF，文件不会出现空洞。

心跳

双方每 5 s ping。守护进程 30 s 没收到任何字节（Seen 包装 stdin 记录最后时间）或 stdin 结束，就杀掉所有进程组并退出——ssh 断开后不会留下孤儿进程。

会话

客户端把在途请求失败为 {code:"unknown", lost:true}，下一次请求时重启。句柄绑定打开它的会话 id，旧句柄绝不会打到新守护进程上。

3. 守护进程各模块

3.1 exec.rs：命令执行

每个管道一个读线程，通过 channel 把 Data/Eof/Exit/WaitFailed/Cancel/Kill 消息送到事件循环；事件循环负责截止时间、进程退出后 100 ms 的 stdio 宽限（EXIT_STDIO_GRACE，防止后台孙进程拿着管道让命令永不结束）、窗口节流以及 spill 文件。结果优先级被写成直白的代码：

// daemon/src/exec.rs
if timed_out {
    return Err(with_spill(Failure::new("timeout", "timeout")));
}
if aborted {
    return Err(with_spill(Failure::new("aborted", "aborted")));
}
if let Some(error) = spill.as_ref().and_then(|spill| spill.failed.clone()) {
    return Err(Failure::new(
        "unknown",
        format!("Failed to preserve complete shell output: {error}"),
    ));
}

即 timeout > aborted > spill 失败 > 退出状态，与 NodeExecutionEnv 相同。字符串命令按 /bin/bash → which bash → sh 的顺序找 shell 并 -c 执行；每个命令新开一个 session，杀进程时对整个进程组发 SIGKILL；被信号杀死的退出码为 128+信号（cleanup 后即 137）。

3.2 window.rs：只传“窗口”里的输出

Agent 往往只关心命令输出的尾部。Window {maxBytes, maxLines, minIntervalMs, bytesPerSecond} 让守护进程只发送调用方会保留的那部分，被跳过的部分以 skipped 计数随 event 送达（客户端放进 ShellOutputInfo.skipped）。完整输出可选择写入远端的 pi-output-<uuid>.log（spill）。测试 “transfers only about a window of output a caller keeps, with exact counts” 校验了计数精确。

3.3 decode.rs：解码细节

StreamDecoder 用 UTF_8.new_decoder_with_bom_removal()——只去掉 UTF-8 BOM，从不嗅探 UTF-16；range_decoder（读取文件中间某个范围）则完全不处理 BOM。这对应 Durable 里同名的 StreamDecoder/rangeDecoder，解码放在离数据最近的地方，分块边界上被切开的多字节字符也不会出错。

3.4 pty.rs：伪终端

openpty 后在 pre_exec 里 setsid + TIOCSCTTY 设置控制终端，重置信号处理并清空信号掩码；TIOCSWINSZ 调整窗口；ptyForeground 用 tcgetpgrp 报告前台作业（测试 “reports the job in the foreground, not the shell at its prompt”）。终端传原始字节而非解码文本。Windows 暂不支持终端。

3.5 watch.rs：监视文件变化

移植自 Durable 的 NodeFileWatcher：基于 notify crate 的原生事件只用来触发防抖（50 ms）后的重新扫描，而不是直接相信事件内容；macOS FSEvents 额外等待 500 ms 稳定。对于 NFS/SMB/CIFS/FUSE/9P 这类不报告远端修改的文件系统（通过 statfs 魔数识别）以及 Windows，改为每 2000 ms 轮询快照。单个监视器最多 10,000 个目录；最近 5 s 内修改且 ≤256 KiB 的文件还会比较内容哈希，以发现 mtime 精度不足时的修改。

    0xfe534d42, // SMB2

客户端 watch.ts 在连接丢失后按 1 s 起、翻倍到 30 s 的退避重开监视，并上报 overflow——明确告诉上层“中间的变化没看到，请全量重扫”，而不是假装什么都没发生。

3.6 scan.rs 与 sys/*

scan.rs 是 Durable LineScanner 的移植，按 64 KiB 块在远端扫描行，避免把整个大文件拉回本地。sys/unix.rs 的杀进程树非常简洁：

// daemon/src/sys/unix.rs
pub fn kill_tree(pid: u32) {
    let pid = pid as i32;
    // SAFETY: plain signal delivery.
    unsafe {
        if libc::kill(-pid, libc::SIGKILL) != 0 {
            libc::kill(pid, libc::SIGKILL);
        }
    }
}

Windows 版见第 7 节。构建方面，Cargo.toml 精确锁定依赖版本（encoding_rs 0.8.42、notify 8.2.0 等），release 配置开 lto、codegen-units=1、strip，以减小要上传的二进制。

4. TS 客户端

4.1 connection.ts：懒启动、会话与重试

  • 启动命令可以是静态数组，也可以是每次启动都重新执行的 async 函数——SSH 部署逻辑正是挂在这里。
  • #connect 不缓存失败的启动：一次失败只让等待这次启动的请求失败，下一次请求重新尝试（测试 “computes the command at each start and retries a start that failed”）。
  • request(op, json, {session}) 若会话已变则直接以 lost 失败；kill() 发送带 mode:"kill" 的 CANCEL。
  • 接收端是分块缓冲区（peek/consume），payload 拷贝成普通 Uint8Array，字符串用 toWellFormed() 规整孤立代理项，保证 JSON 能被 Rust 端的 serde 接受。

4.4 terminal.ts

openTerminal(connection, options) 返回 RemoteTerminal：输入按块走 ptyWrite，resize 走 ptyResize，foreground() 带会话 id 请求 ptyForeground；程序退出、close() 或连接丢失（守护进程会杀掉它）时终端结束。localDaemon() 还能让本地会话也用守护进程提供终端。

5.2 按内容寻址的部署

// src/ssh.ts
/** Where a daemon with this content lives on the remote machine: named by its SHA-256, so versions never collide. */
function daemonPath(remote: RemotePlatform, sha256: string): string {
  const name = `pi-env-${sha256.slice(0, 32)}`;
  return remote.platform === "windows"
    ? `${remote.home}\\.pi\\mobile\\tools\\${name}.exe`
    : `${remote.home}/.pi/mobile/tools/${name}`;
}

  • 先写临时文件、校验通过再原子 mv，所以目标路径上永远只会是完整且正确的二进制。

5.3 两种入口与主机密钥流程

sshConnection()：懒

首个请求才连接。失败（断网、主机密钥不受信或已变）让等待中的请求以 spawn_error 失败，消息是 ssh 的诊断输出；下一个请求重试。

connectSsh()：急

立即探测并部署，失败直接 reject；主机密钥必须已经受信，否则抛 HostKeyUnknownError。

信任主机密钥是显式的三步：scanHostKey 用 accept-new 连到一个临时 known_hosts 文件拿到密钥行，并用 ssh-keygen -lf 算指纹给用户确认 → acceptHostKey 写入目标的 known_hosts → 之后所有连接都用 StrictHostKeyChecking=yes。acceptHostKey 只接受“别名 类型 密钥”的纯文本行（拒绝标记、通配符、哈希主机名），同类型密钥不同则抛 HostKeyChangedError——必须先 forgetHostKey，绝不静默替换。known_hosts 的修改按文件串行，并通过“临时文件 + rename”原子完成。

6. SSH 加固清单

sshArguments 生成的参数几乎把所有可能“意外放大权限”的 ssh 特性都关了：

不转发任何东西

-T -a -x，ClearAllForwardings，ForwardAgent=no，ForwardX11=no：远端拿不到你的 ssh-agent 或 X 显示。

不被用户配置劫持

ControlMaster=no/ControlPath=none，RemoteCommand=none，PermitLocalCommand=no，SendEnv=-*；可选的 configFile 路径会加引号并转义 %。

严格的主机身份

BatchMode=yes（永不交互提示），StrictHostKeyChecking=yes，独立 UserKnownHostsFile、GlobalKnownHostsFile=none、HashKnownHosts=no、HostKeyAlias，IdentitiesOnly。

参数注入防护

checkField 拒绝以 - 开头或含空白的 host/user 等字段，并在 host 前放 --；另有 ServerAliveInterval=15，SSH 超时 60 s、上传 300 s。
守护进程默认不经登录 shell 启动（ssh 本身就不用登录 shell）；需要 ~/.profile 里的环境时设置 loginShell: true，启动命令变为 exec "$SHELL" -lc 'exec "$0" "$@"' <daemon>，参数通过 $0/"$@" 传递，避免二次拼接引号。

7. Windows 与 Termux 细节

  • 平台探测：先发 POSIX 探测，失败（远端 shell 是 cmd/PowerShell）再用 powershell -NoProfile -NonInteractive -EncodedCommand（UTF-16LE base64，免去引号地狱）；若 uname 返回 MINGW/MSYS/CYGWIN（Git Bash 是默认 shell），仍改问 PowerShell 获取真实架构和 home。最后用 echo %OS% 是否展开来区分 cmd 与 PowerShell，决定启动命令写成 & 'path' 还是带引号路径。
  • 进程（daemon/src/sys/windows.rs，遵循 libuv）：所有子进程放进 job object（KILL_ON_JOB_CLOSE、BREAKAWAY_OK、DIE_ON_UNHANDLED_EXCEPTION），守护进程退出即全部清理；kill_tree 调 taskkill /F /T /PID；读线程用 CancelSynchronousIo 打断；CREATE_NO_WINDOW。
  • 命令：字符串命令走 Git Bash（配置的 shell → Git Bash → where bash.exe），会识别旧版 WSL bash 并改用 stdin 传命令；argv 命令按 libuv 的 search_path 直接解析，并像 Node 一样拒绝 .bat/.cmd（无 shell 时批处理参数转义不安全）；参数按 libuv 的 quote_cmd_arg 拼接。
  • 监视：Windows 一律轮询。
  • Termux：tmpdir 用 $PREFIX/tmp；探测会警告未设置 TMPDIR、未加载 termux-exec（#!/usr/bin/env 脚本会失败），并提示用 termux-wake-lock 防止 Android 挂起。

9. 值得借鉴的设计

  1. 语义放客户端，系统调用放守护进程。守护进程保持“薄”，Node 的路径/错误/结果规则在 TS 里只实现一次，再用一致性测试 + 差分随机测试锁死行为。
  2. 二进制帧 + 双队列背压。JSON 头 + 原始 payload 免 base64；控制帧插队、批量输出 4 MiB 上限，保证大量输出时心跳与取消依然及时；“先登记再执行”消除取消竞态。
  3. 按内容寻址、每次启动前校验。以 SHA-256 命名、临时文件校验后原子替换，多版本共存不冲突，被篡改的二进制会被发现并替换。
  4. 失败是一等公民。懒连接 + 不缓存失败的启动、会话绑定的句柄、lost 标记、watch 的 overflow、30 s 无声自杀并杀进程组——每一种断线都有明确、可观察的结果。
