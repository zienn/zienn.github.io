1. 持久执行是什么，Agent 为什么需要

“持久执行”（durable execution）指：一段多步骤的工作在进程崩溃、重启、迁移后，能从已持久化的进度继续，而不是从头开始或悄悄丢失。Agent 恰好是这种工作的典型：一次 run 可能包含几十轮模型调用和工具调用，持续数小时；中途笔记本休眠、容器重新部署、OOM 都很常见。

官方博文给出的目标很具体：一个“能在任何地方运行、可从不同界面接入、支持无限长对话、能扛住灾难性内外部故障、并允许多人同时操控同一个 Agent”的 harness。它与 Pi 编码 Agent 并列而非替代：后者面向终端里单人使用，崩了“你看一眼然后让它继续”；Pi Durable 是用来构建任意 Agent 应用（包括编码 Agent）的框架。

规范开篇的核心规则只有一句：

// docs/spec.md
A Session atomically commits immutable entries, full task records, and
Chord-tracked documents. Only committed state is observable.

“只有已提交的状态可见”——UI 看到的流式输出、工具进度也都是已落盘的（默认至多 100 ms 一次），崩溃最多丢掉最后一个节流窗口。

3. 核心模型：检查点状态机，而不是事件重放

这是理解 Pi Durable 最关键的一点。Temporal 一类系统把工作流写成普通代码，靠事件历史 + 确定性重放恢复（这是对其公开文档的通用描述，本文未逐条核实）。Pi Durable 的规范在“非目标”里明确写着没有 “Session-kernel semantic event journal”。它的单位是任务：一个显式的、由若干 phase 组成的状态机，状态（checkpoint）是你自己定义的 JSON。

3.1 任务状态

stateDiagram-v2
  [*] --> pending: createTask
  pending --> running: 调度器保留
  running --> running: commit 新 checkpoint
  running --> sleeping: sleepUntil
  sleeping --> pending: 时钟到 until
  running --> waiting: waiting on 子任务
  waiting --> pending: 子任务全部终结 / failFast
  running --> completing: 结果已定但仍有自有工作
  completing --> terminal: 自有工作排空
  running --> terminal: completed / failed / aborted
  running --> pending: 崩溃后重开 restarts+1
  pending --> pending: restarts 达上限 → 停放 blocked
  terminal --> [*]

类型定义直接来自规范（节选）：

// docs/spec.md §5.1
type TaskState<S, R> =
  | { readonly status: "pending"; readonly checkpoint: S }
  | { readonly status: "running"; readonly checkpoint: S }
  | { readonly status: "waiting"; readonly checkpoint: S; readonly on: readonly TaskId[]; readonly policy: JoinPolicy }
  | { readonly status: "sleeping"; readonly checkpoint: S; readonly until: number }
  | { readonly status: "completing"; readonly outcome: TaskOutcome<R> }
  | { readonly status: "terminal"; readonly outcome: TaskOutcome<R> };

注：状态图中“sleeping/waiting → pending”是本文为便于理解的画法；规范只说它们到点或子任务结束后“resumes at checkpoint”，未必经过名为 pending 的持久状态（未核实）。

3.2 “phase 从头重跑”——这就是确定性规则

没有“工作流代码必须确定”这种全局约束，取而代之的规则更朴素：一个 phase 在重启后从顶部重新执行，所以 phase 内部没有可恢复的中间点。README 关于睡眠的一段说得很直白：

// README.md — Sleeping and Waking Up
There is no sleep in the middle of a phase: a phase reruns from its top after a restart,
so work after the wait goes in the next phase, and what it needs goes in the checkpoint.

也就是说，你要把“等待之后的工作”放进下一个 phase，并把它需要的数据放进 checkpoint。

3.3 效果三明治（effect sandwich）

// docs/spec.md §5.2
commit intent phase
perform external effect
commit outcome or next phase

规范紧接着说明：重开时处于 intent phase，意味着副作用可能已经发生，phase 处理器要么安全重试、要么轮询外部句柄、要么记录“被中断”。规范的不变式 4 也规定：外部副作用绝不在 Session 事务内执行。

3.4 memo：首写者胜出的幂等原语

memo 是存放在任务记录里的小值，插入候选与读取胜者在同一次提交中完成，“首写者胜出”。test/examples/13-recovery.ts 用它避免崩溃后重复打印：

// test/examples/13-recovery.ts
tick: async (task, runtime, taskContext) => {
  const n = task.state.checkpoint.n;
  // Save the intent before the effect. …
  if ((await runtime.memo(`printed-${n}`, taskContext)) === undefined) {
    await runtime.memo(`printed-${n}`, true, taskContext);
    console.log(`tick ${n}`);
  }
  …
  await runtime.sleepUntil(runtime.now() + 50, { phase: "tick", n: n + 1 }, taskContext);
},

注意：memo 先写再打印，若崩溃发生在两者之间，这一行就不会再打印——它把“至少一次”换成了“至多一次”。对真实外部系统，博文的支付示例用的是另一种做法：把 payment-${task.id} 作为幂等键交给银行接口。

3.5 定时器与等待

  • 睡眠：runtime.sleepUntil(until, nextCheckpoint) 以提交结束当前 phase，任务不占用调用，跨重启存活；到时从 checkpoint 继续。重试退避、deferred 响应轮询都用同一机制。
  • 时钟：通过 now / setTimer 注入，可用假时钟测试。README 提醒：睡眠截止时间按 now 存储，打开同一存储的所有进程必须使用同一时钟。
  • 等待子任务：提交 { status: "waiting", on, policy }，allSettled 等全部结束，failFast 首个失败即中止其余。
  • 可被驱逐的宿主（如 Cloudflare Durable Object）：传 onWake，Harness 不再自设定时器，而是把 { active, at } 告诉宿主去设闹钟，闹钟触发时调用 resume()。

Pi Durable 没有名为“signal”的原语；外部输入通过 submission 进入（input / write，whenBusy 可选 follow-up、steer、reject），带 requestId 的提交只会被受理一次。

4. 崩溃恢复全流程

sequenceDiagram
  participant C as 客户端
  participant H as Harness / Session
  participant S as Storage
  participant M as 模型
  participant T as 工具
  C->>H: submit(input, requestId)
  H->>S: commit pi.user + 创建 pi.generation
  H->>S: generation: prepare → request（固定 model/cutoff）
  H->>M: 流式请求
  H->>S: 每 ≤100 ms 提交 partial 到 pi.live
  H->>S: commit pi.assistant(tool calls) + 创建 pi.tool × n，进入 waiting
  H->>S: tool: call → commit intent（phase execute, 参数, replay 策略）
  H->>T: execute()
  Note over H,T: 进程崩溃
  C->>H: 新进程 Harness.open + resume()
  H->>S: 存活的 running 记为 pending，restarts+1
  alt replay = "safe"
    H->>T: 用存储的参数重新 execute（不再跑 beforeTool）
  else 非 safe
    H->>S: commit interrupted 错误结果（含已提交的部分输出）
  end
  H->>S: generation 恢复，模型看到结果后继续
  C->>H: submit(同一 requestId) → 返回原 submission

几条关键规则（均出自 docs/spec.md）：

  • 模型请求（§8.3）：request 先把上次中断留下的 partial 转成一条 aborted 的 pi.assistant 条目，再用同样已提交的消息、同样固定的模型、思考级别和流参数重新请求。可重试错误按策略睡眠退避；deferred 结果进入 poll phase 定时 fetchDeferred()。
  • 工具调用（§8.4）：call phase 校验参数、跑 beforeTool，然后一次提交记录意图并转入 execute。execute phase 只会被恢复路径到达：当存储的与当前的策略都是 safe 才重跑，否则写入 interrupted 错误结果。
  • 崩溃循环（§5.4）：打开存储时，每个残留的 running 任务被写回 pending 且 restarts 加一；正常 close 不计数；任务提交了不同的新状态才清零。达到 restartLimit（默认 5）就被停放（blocked: restart_limit），并以 task_parked 报告。
  • 存储错误是致命的（README Errors）：命中存储错误后整个 Harness 失败并自行关闭，不做重试；宿主应监听 harness.closed 并重新打开。

恢复过程的可运行演示就是 test/examples/13-recovery.ts：它在打印 tick 2 后、下一个检查点保存前关闭 Harness，再开一个新 Harness 继续数到 5。

5. 工具与 LLM 调用如何变得“持久”

5.1 replay 策略

官方博文里的一组对比最能说明设计取舍：

// earendil.com/posts/pi-durable（博文示例，节选）
const searchIssues = defineTool({
  name: "search_issues",
  …
  replay: "safe", // only reads, so a rerun after a crash is fine
  …
});
const deploy = defineTool({
  name: "deploy",
  …
  // No replay: a deploy interrupted by a crash is reported to the model,
  // never repeated.
  execute: async (args) => ({ … }),
});

默认不是 safe：被中断的调用不会被盲目重做，而是把“被中断 + 已有输出”作为错误结果交给模型，让模型决定下一步。这是 Agent 场景特有的一种恢复方式——把不确定性交还给推理者。

5.2 嵌套调用与 key

工具可用 api.executeTool() 调用其他工具，嵌套调用是调用者拥有的独立工具任务。每个嵌套调用有一个 key（默认是它在调用者嵌套调用中的序号）。README：一个 replay-safe 的调用者在崩溃后重跑、按相同顺序（或相同 key）调用时，会拿回已经发起的嵌套调用，而不是再启动一次。

5.3 Code Mode：唯一用到确定性重放的地方

Code Mode 让模型写 JavaScript，在 QuickJS 沙箱里以 await tools.x() 调用工具。这里才出现了 Temporal 式的确定性重放：

// src/codemode/codemode.ts（文件头注释节选）
 * Solution: deterministic replay (`CodemodeSandboxBase.start()` in pi-codemode). The VM only runs when the host hands
 * it a result; given the same start data, clock, seed, and results in the same order, it makes the same calls with
 * the same arguments. The tool is replay-safe: after a restart, `execute()` runs again, starts the script again from
 * the stored start data, and hands it the results it got before, in the order it got them, from a journal written
 * before each delivery.

沙箱用虚拟时钟、带种子的随机数和 UTC 保证确定性；脚本在重放时若调用顺序与 journal 不符（发散），或模块版本/VM 指纹变化、截止时间已过，则拒绝重放并以错误结束该调用。

5.4 hooks 也要考虑重跑

博文的审批示例：beforeTool 钩子可能在崩溃后再次运行，因此把“已批准”存进 memo，重启后直接读到结论而不是再问一次人。

6. 并发、取消与所有权

  • 单写者：所有提交走一条 mutation line；commit 回调里不得 await 模型、工具、网络或人（spec §12 “Long transactions”）。存储同一时间只能被一个进程拥有，没有跨进程锁（README Storage）。
  • 多对话并发：一个 Harness 同时跑任意多个对话；fork 在指定条目处共享父历史。
  • 工具并行：settings.toolExecution 默认 "parallel"；一轮中只要有一个 sequential 调用，整轮按顺序执行（spec §7.3）。
  • 所有权树（spec §5.5）：每个任务在创建时声明所有者（对话或另一个任务），不可变。“中止向下传递”，且任务只有在其自有工作排空后才会终结（completing 状态）。中止是自底向上的：先中止子任务，再运行自身的 abort 处理器，“so each task undoes its own effects”。
  • background：后台任务是边界，不阻止对话空闲，也不被普通中止触及，适合长期子 Agent 或“明天触发的提醒”。
  • Context 取消 ≠ 中止工作：取消一个调用者的 Context 只取消那个等待；要持久地中止共享工作必须提交 abort 标记（spec §5.4）。

7. 版本与热重载

任务与文档都带 version。调度器每次启动任务调用时按记录的 kind 从当前 registry 快照解析定义：

// docs/spec.md §5.4
restarts at restartLimit           -> stay pending, blocked: restart_limit
definition missing                 -> stay pending, blocked: missing_task
stored version newer than it       -> stay pending, blocked: task_too_old
stored version older than it       -> migrate(input, checkpoint, storedVersion)
  failure                           -> stay pending, blocked: migration_failed
  success                           -> commit migrated record + running atomically
equal version                       -> commit running

因为对话里只存扩展和工具的名字，registry 可以在运行中替换（同名 install 即替换）：已在运行的工具调用用旧代码跑完，下一 phase/请求/调用用新代码。文档迁移是“按访问驱动”的纯函数 migrate()，打开 Harness 时不做全量扫描（spec §3.6）。这与 Temporal 需要为工作流代码做版本分支的思路不同（后者为通用描述，未核实）：Pi 的迁移对象是显式的 checkpoint 数据而非执行历史。

8. 存储后端

后端要点（README Storage）
Memory不持久化，适合测试。
SQLite（Node）单文件，WAL + synchronous = NORMAL：扛进程崩溃；断电/宿主故障可能丢最新提交。长时间运行的 Agent 推荐它。
JSONL目录内追加写；{ fsync: true } 在每个提交标记前刷盘；整个历史也驻留内存。
Cloudflare DO SQLiteDurable Object 的 SQLite，提交即其存储事务；可用 prefix: "pi_" 与宿主表共存。

SQLite/JSONL 核心不依赖 Node API，可跑在 Bun 或 Durable Object 里。自定义后端可用 registerStorageConformance() 跑共享一致性测试。Cloudflare 官方文档（2026-10-12 更新）还提供了 Agents SDK 的 PiHarness（beta），用 Lifecycle 任务做心跳与唤醒。

9. ExecutionEnv：Node 与远程

工具只通过调用的执行环境接触文件与进程。env 函数会在每次工具调用、section 渲染时构建环境，拿到对话 ID、对话的 cwd 与已提交读取：

// test/examples/29-sandbox-per-conversation.ts
env: async ({ conversationId, read }, envContext) => {
  const sandbox = await read.snapshot(Sandbox, conversationId, envContext);
  return sandbox?.path === undefined ? undefined : new NodeExecutionEnv({ cwd: sandbox.path });
},

换成远程只需返回 pi-env 的 RemoteExecutionEnv：Durable worker、存储与凭据留在本地，工具跑在 SSH 另一端的 Rust 守护进程里（详见本站的 pi-env 源码精读）。pi-env 的 README（同一提交）给出的组合：

// packages/env/README.md
const { connection } = await connectSsh(target);
const env = new RemoteExecutionEnv({ connection, id: "pi-env:gpu", cwd: "/home/me/project" });
  • id 很重要：edit 与 write 按环境 id + 路径串行化同一文件的修改；“相同 id 看到相同路径下的相同文件”。
  • 两者都能用 registerEnvConformance() 自检——pi-env 正是用这套测试证明与 NodeExecutionEnv 语义一致。
  • 规范的一个陷阱：恢复后重跑的工具会重新构建环境，用的是对话当前的 cwd，可能与第一次不同（spec §12 “Environment on recovery”）。

11. 实践：从最小例子到长时间运行的编码 Agent

这个模式把“重跑安全”落到实处：重跑时先查是否已有子对话，提交用 requestId: `subagent:${api.taskId}` 去重。

11.4 远程环境

把 env 换成返回 RemoteExecutionEnv 的函数（见第 9 节）。懒连接的 sshConnection() 会让 SSH 失败成为那次工具调用的错误结果，下一次调用再试，恰好与工具任务的错误语义相容。

12. 陷阱与最佳实践

副作用别放进 commit

commit 回调持有提交线；不要在里面 await 模型、进程、网络或人。在 commit 里读 snapshot() 之类会排队等提交线，可能永远不返回（spec §12）。

默认不 safe

只有只读或天然幂等的工具才声明 replay: "safe"；有外部写入时用幂等键（如 task.id）或 memo 记录决定。

checkpoint 里放续跑所需的一切

phase 会从头重跑；等待之后的工作放到下一个 phase。

大结果别放终态记录

终态记录长期可查；大结果放条目或文档，只在 outcome 里存 ID。

单进程拥有存储

没有跨进程锁，多个 worker 打开同一存储是未定义的使用方式；横向扩展按“会话→进程/DO”分片（推论，非官方表述）。

稳定的 prompt

section 输出若每次都变（如嵌入当前时间）会追加 system 增量并让提供方的 prompt cache 失效。

监听 closed 并重开

存储错误会终结 Harness；重试应在自定义 Storage 内部做。

文档要设 checkpointWhen

() => false 会让增量回放无界增长（spec §12 “Checkpoint starvation”）。

13. 小结

  1. “只有已提交的才可见”是一切的地基：UI、流式输出、子 Agent 状态都从持久状态派生，崩溃后看到的就是真实进度。
  2. 检查点状态机代替事件重放：开发者显式划分 phase、自定义 checkpoint，迁移的是数据而非历史；确定性重放只在 Code Mode 这种“脚本”场景局部使用。
  3. Agent 化的副作用语义：非 safe 工具中断后不重做，而是把“被中断 + 部分输出”交给模型；模型请求则用固定参数重发，partial 作为 aborted 条目保留。
  4. 所有权树统一了取消与清理：子任务、子对话、后台边界与自底向上的 abort，让子 Agent、并行支付这类结构天然可恢复。
  5. 可移植的底座：小巧的 Storage 与 ExecutionEnv 接口 + 一致性测试，让同一 harness 跑在 Node、Bun、Cloudflare DO 上，并通过 pi-env 把工具放到远端机器。
